# SPEC-0005：质量、测试与交付标准

状态：Accepted baseline。日期：2026-10-18。

## 1. 工程质量
- TypeScript 类型检查和 ESLint 必须通过，保留无障碍规则。
- 依赖安装使用冻结锁文件；依赖变更必须同时审查并提交 pnpm-lock.yaml。
- 公共组件必须有稳定、清晰的 props 契约，不得硬编码业务 API、路由或领域规则。
- 所有可见交互必须有真实行为；不允许死按钮、无说明占位页或误导性的静态数据。

## 2. 测试分层
- 纯工具：查询参数解析、格式化、导出转义、日期、环境变量和错误映射。
- 公共组件：DataTable 选择/排序/分页/列显隐/密度、表单容器、状态标签、命令面板、上传和异步状态。
- API/MSW：分页、搜索、筛选、排序、参数校验、唯一性、关联约束和 CRUD。
- 页面：仪表盘、客户、项目、订单、用户列表/详情/编辑及危险操作和错误路径。
- 集成：URL 状态恢复、浏览器历史、Query 缓存失效、主题和导航。
- 测试验证用户可观察行为，避免过度依赖内部实现或脆弱 CSS 类名。

## 3. 覆盖率策略
首期不设全局覆盖率百分比硬门槛，但必须生成覆盖率报告。新增复杂逻辑、公共组件契约或关键业务规则时，应补充针对性测试。不得通过关闭 CI 检查解决失败。

## 4. 交付命令
交付前执行：pnpm install --frozen-lockfile、pnpm lint、pnpm typecheck、pnpm test、pnpm test:coverage、pnpm build。所有命令必须成功。GitHub Actions 对 push 和 pull request 执行对应门禁。

## 5. 文档与变更管理
- 新功能先更新 SPEC 与验收条款，再实现。
- 改变技术栈、状态边界、API 契约、导航结构或公共组件行为时更新 ADR。
- 如果只完成文档或设计阶段，应明确标记未执行的运行验证。
- 已确认决策与实现冲突时，记录差距并安排修复；不得改写 SPEC 让不符合规范的代码变成“符合规范”。
